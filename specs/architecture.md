# Architecture

> Related specs: [agents](agents.md) · [workflows](workflows.md) · [data-model](data-model.md)

## Multi-Agent Architecture

All workflows run as a hierarchy of agents. The goal is to keep each agent's context window small and focused — no single agent loads the entire vault or holds all inbox files at once.

```
User / CLI
    │  (only this layer may invoke nono run)
    │
    │   Script pre-flight:
    │     pre-screen.py  → removes bare URLs / empty files from work list, writes review entries
    │     check-review.py → classifies each inbox file:
    │                         ready      — no review entry, proceed normally
    │                         has-answers — answered entry exists, pass to orchestrator + flag editor
    │                         blocked    — unanswered entry exists, skip entirely this run
    │
    ├─► Orchestrator session (nono: vault/ read-only)
    │       Receives: list of ready + has-answers inbox files only
    │       Reads content, spawns Quick Search sub-agents, emits JSON work plan → stdout
    │
    │   Script reads + validates JSON work plan
    │   Script pre-creates staging subdirectory per agent
    │
    ├─► Editor session × N (one nono run per inbox file)
    │       nono: vault/ (r) + inbox/$FILE (r) + inbox/staging/$AGENT_ID/ (rw)
    │             + _meta/review.md (rw, only if REVIEW_HAS_ANSWERS=true for this file)
    │       Writes one or more output files to its staging subdirectory
    │       Never touches vault content folders directly
    │
    │   Script reads staging files, validates paths, moves to vault
    │   Script updates _meta/tags.md and _meta/review.md
    │   Script removes processed inbox files
    │
    └─► Q&A agent session (nono: vault/ read-only [+ queries/$SLUG rw if --save])
```

Every agent runs inside a **nono sandbox**. Each sandbox is granted only the paths it actually needs — no agent can read or write beyond its declared scope. This is enforced at the OS level and cannot be bypassed from within the session.

**Critical security constraint:** The AI must never initiate a new `nono run`. Doing so would allow an agent to define its own sandbox permissions and expand its own access. `nono run` is exclusively invoked by the user-controlled script. Within a nono session, Claude may use the `Agent` tool to spawn sub-agents — those inherit the same sandbox and cannot expand it.

**No AI writes to the vault.** File agents write only to their assigned staging subdirectory and `_meta/review.md` (for cleanup only). The user-controlled script is the sole process that moves content into vault folders, updates `_meta/tags.md`, and removes inbox files. This ensures all vault mutations are deterministic, path-validated operations under user control.

## Sandbox Permissions (nono)

Paths follow the principle of least privilege. `--read` and `--read-file` are used wherever write access is not needed. `--allow-file` (read+write on a single file) is used for single-file grants; `--allow` on a directory is scoped to the smallest possible subtree.

### Orchestrator sandbox

```bash
nono run \
  --read $VAULT \                 # full vault read — inbox listing + obsidian CLI search
  -- claude --print "..." < orchestrator-prompt.md
```

The orchestrator gets full vault read (required for obsidian CLI to traverse the vault) and nothing else. It emits a JSON work plan to stdout — no files written. The script captures stdout.

### File agent sandbox (one per inbox file)

```bash
# When REVIEW_HAS_ANSWERS=false for this file:
nono run \
  --read $VAULT \                               # full vault read — see note below
  --allow $VAULT/inbox/staging/$AGENT_ID/ \     # agent's private staging subdirectory
  -- claude --print "..." < editor-prompt.md

# When REVIEW_HAS_ANSWERS=true for this file:
nono run \
  --read $VAULT \
  --allow $VAULT/inbox/staging/$AGENT_ID/ \
  --allow-file $VAULT/_meta/review.md \         # read answered questions + remove resolved entries
  -- claude --print "..." < editor-prompt.md
```

**Why `--read $VAULT` and not individual `--read-file` grants:**

The orchestrator's work plan typically lists 5–15 related vault files for the editor to read — the exact set is only known at runtime, after the orchestrator has run. Granting `--read-file` for each one would require the script to iterate the JSON and build a flag per file, and still wouldn't cover the obsidian CLI which must traverse the full vault to execute searches. `--read $VAULT` covers both needs with a single grant. Write access remains tightly scoped — the agent can only write to its private staging subdirectory and (conditionally) `review.md`.

The inbox file itself (`inbox/$FILE`) is included under `--read $VAULT`, so no separate `--read-file` grant is needed for it either.

`$AGENT_ID` is a unique identifier generated by the script. The script creates the staging subdirectory before launching the session. The agent may write as many files as it needs within that subdirectory — one per output note.

`review.md` access is granted only when `check-review.py` confirmed answered entries exist for this file. Access is for reading answers and removing resolved entries only — new review questions go to `_review.md` in staging, avoiding write races between parallel agents.

### Q&A agent sandbox

```bash
nono run \
  --read $VAULT \                          # full vault read — obsidian CLI search
  --allow-file $VAULT/queries/$SLUG \      # only if --save; pre-created by script
  -- claude --print "..." < qa-prompt.md
```

If `--save` is requested, the script pre-creates the target query file and grants `--allow-file` on that specific path.

### What the script does (no sandbox)

The user-controlled script runs outside any nono session and holds full filesystem access. It is responsible for:

- Pre-creating `_meta/review.md` if it does not exist
- Running `pre-screen.py` — removes bare URLs and empty files from the work list, writes their review entries to `_meta/review.md` directly
- Running `check-review.py` — classifies every inbox file as `ready`, `has-answers`, or `blocked`; computes a per-file `REVIEW_HAS_ANSWERS` flag
- Passing only `ready` and `has-answers` files to the orchestrator; skipping `blocked` files entirely this run
- Validating every path in the orchestrator JSON (must be within `$VAULT`, no traversal, correct content folder for the declared `type`)
- Pre-creating a staging subdirectory per editor agent before spawning it
- Passing the per-file `REVIEW_HAS_ANSWERS` flag and the work plan entry in each agent's prompt context
- Granting `--allow-file $VAULT/_meta/review.md` to editor agents only when their file's `REVIEW_HAS_ANSWERS` is `true`
- Reading all staging output files across all agent subdirectories and validating their frontmatter
- Moving staging output files to their declared `target` path (create or overwrite), stripping the `staging` block
- Appending all staged `_review.md` entries to `_meta/review.md`
- Updating `_meta/tags.md` with any new tags declared in staging frontmatter
- Removing successfully processed inbox files
- Cleaning up `inbox/staging/`

### Sandbox configuration

The vault path and tooling repo path are set once in a `.env` file (or exported shell variables) and referenced as `$VAULT` and `$TOOLING_REPO` in all nono invocations.
